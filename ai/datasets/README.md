# ChainGuard Dataset Platform

Sprint AI-2: a real, working synthetic dataset generator, augmentation framework, quality validator, real-data collector, versioning, and metadata management — built to support future model training, not to train anything itself (no training or inference exists in this sprint).

## What's in the repo right now

A **small representative sample**, generated by the tools below, not hand-picked: 30 images (5 per class × 6 classes), at `ai/datasets/synthetic/`, with `ai/datasets/manifest.csv` and `ai/datasets/versions.json` (version `v1`). This exists to prove the pipeline works end-to-end and to give you something to look at immediately — it is **not** a training-ready dataset (see "Generating datasets of any size" below for how to make one).

## Generating datasets of any size

This is the same answer whether you want 30 images or 3,000 — **only the config file changes**:

```bash
cd ai
python -m datasets.generator.cli --config datasets/configs/sample.yaml               # 30 images (ships in the repo)
python -m datasets.generator.cli --config datasets/configs/production_example.yaml   # 3,000 images (full training scale)
```

To generate a custom size, copy either config and edit `images_per_class`:

```yaml
image_size: [640, 640]        # 320x320 for quick iteration; 640x640 for actual YOLOv8 training
images_per_class:
  SAFE: 500                    # any number, per class, independently
  TORN: 500
  OPENED: 500
  CRUSHED: 500
  TAPED: 500
  PARTIAL_DAMAGE: 500
output_dir: datasets/synthetic
seed: null                     # null = a fresh random set each run; an integer = reproducible
apply_augmentation: true
generator_version: v1.0.0      # bump this when you change the generation pipeline itself
```

Then: `python -m datasets.generator.cli --config path/to/your_config.yaml`

Generation time scales roughly linearly — the 30-image sample takes well under a second; the recommended production size (docs/chainguard-ai-technical-design-phase3a.md, Step 5: 300–500 train / 60–100 val / 60–100 test per class, ≈2,500–4,000 total) should take well under a minute on ordinary hardware, since this is pure PIL/numpy image synthesis, not a GPU-bound operation.

Each run appends to the existing manifest and cuts a new dataset version automatically — running the generator twice doesn't overwrite anything, it grows the dataset.

## Checking what you generated

```bash
python -m datasets.stats_cli --manifest datasets/manifest.csv
```
Reports per-class counts, source (synthetic/real) breakdown, missing classes, and flags class imbalance (default: warns if any class has 3x+ more images than another).

## Importing real images

Two-stage, deliberately never fully automatic (see `datasets/collector/collectors.py`'s docstring for why):

```python
from datasets.collector.collectors import BatchImporter
from datasets.manifest import DatasetManifest

# Stage 1: quality-check + de-duplicate a folder of images, stage the
# survivors into a pending-review directory with auto-generated names.
result = BatchImporter().import_directory(
    source_dir="path/to/raw/photos",
    pending_review_dir="datasets/pending_review",
)
print(f"{len(result.imported)} imported, {len(result.rejected)} rejected, {len(result.duplicates)} duplicates")

# Stage 2: after a human looks at datasets/pending_review/ and decides the
# class for each file, confirm them into the real manifest.
manifest = DatasetManifest("datasets/manifest.csv")
BatchImporter().confirm_labels(
    pending_review_dir="datasets/pending_review",
    labels={"TORN_batch_import_20260801T120000_a1b2c3d4.jpg": "TORN"},
    manifest=manifest,
    annotator="your-name",
)
manifest.save()
```

Webcam capture (`datasets/collector/collectors.py`'s `WebcamCollector`) follows the same real interface but needs a physical camera to actually run — **not exercised by this sprint's tests** since no camera exists in a CI/sandbox environment; see that class's docstring.

## Why Pillow/numpy instead of Albumentations for augmentation

The Phase 3A design document named Albumentations as the augmentation tool. This sprint deliberately used Pillow + numpy instead — a documented deviation, not a silent one. Albumentations' main advantage is *bounding-box-aware* augmentation for training pipelines, and no training exists yet in this project; pulling in Albumentations (and its opencv-python-headless dependency) now would repeat exactly the mistake Sprint AI-1's `requirements.txt`/`requirements-ml.txt` split was built to avoid — installing a library nothing imports. `requirements-ml.txt` still has Albumentations versioned and ready for whichever future sprint actually needs bbox-aware augmentation during training.

| `datasets/augmentation/augmentor.py` | Rotation/brightness/contrast/noise/blur/compression | Real |
| `datasets/validator/quality_validator.py` | Resolution/blur/brightness checks, perceptual-hash dedup | Real |
| `datasets/statistics/dataset_stats.py`, `stats_cli.py` | Per-class/source counts, imbalance warnings | Real |

| `datasets/collector/collectors.py` (`WebcamCollector`) | Live camera capture | Real code, **not testable in this environment** |

## What this sprint does NOT do

Train a model. Run inference. Split the dataset into train/validation/test folders (the design document's Step 5 folder structure lists `train/`/`validation/`/`test/` as generated-not-hand-curated by a *future* splitting tool that reads `manifest.csv` — that tool doesn't exist yet, deliberately, since there's no training pipeline yet to consume the split). Auto-label anything without a human confirming it.
