# ChainGuard

AI-Powered End-to-End Examination Paper Integrity Monitoring System — a CSE capstone project architected to also hold up as a realistic, professionally-structured system.

ChainGuard tracks a sealed examination envelope from printing through storage, transport, and arrival at the exam center, combining computer-vision damage detection, QR-based chain-of-custody tracking, GPS/transport monitoring (simulated where real hardware isn't available), live alerts, and reporting into one platform.

## Repository layout

```
chainguard/
├── backend/    Express + Prisma + PostgreSQL + Socket.IO REST API
├── frontend/   React + Vite + Tailwind dashboard
├── ai/         FastAPI AI service (Sprint AI-1: infrastructure only, no model yet)
└── (simulation/  — planned for a later phase, not yet built)
```

Each half has its own `README.md` with setup details specific to that service — this file covers running the whole system together and tracks overall project status.

## Quick start

You need PostgreSQL running locally (or point `DATABASE_URL` at one).

**Backend:**
```bash
cd backend
cp .env.example .env      # edit DATABASE_URL / JWT secrets if needed
npm install
npx prisma migrate dev     # applies both existing migrations (Phase 1 + Phase 2)
npm run prisma:seed        # creates demo users (one per role), cameras, envelopes, detections, alerts, audit log entries
npm run dev                 # http://localhost:5000
```

**Frontend** (separate terminal):
```bash
cd frontend
npm install
npm run dev                 # http://localhost:5173
```

Log in with a seeded account — see `backend/README.md` for the full list and default password.

**Critical Bug Fix — Live GPS Simulation Breaking on Page Navigation: done.** Re-verified directly (not re-assumed) that the backend simulation genuinely has zero dependency on any frontend connection — traced the current code rather than trusting the earlier report. The real bug was entirely on the frontend: `TransportMonitoring.jsx` had no way to discover an already-running session on mount, so it auto-selected fresh defaults every time, which on a return visit is often the exact vehicle the still-running simulation already marked `IN_TRANSIT` — the reported error was the pre-existing backend safeguard correctly doing its job with nothing checking first. Fixed entirely from two endpoints that already existed: `GET /gps/live` discovers an active session on mount, `GET /gps/history/:sessionId` restores the full view (map, route, checkpoints, simulation state) before the user sees anything. A second, independent safeguard re-checks at the button level, covering a session started in another tab. No backend file changed, no new endpoint created. Confirmed by grep that unmounting never stops the backend (`stopTransport`/`pauseTransport` only ever called from explicit button handlers). See `docs/chainguard-critical-bugfix-gps-navigation.md`.

**Critical Bug Fix — "Vehicle already on an active transport session" With No Active Sessions: done.** Traced every write to `Vehicle.status` directly and found the real root cause: neither the backend's duplicate check nor the previous fix's button label ever queried the actual `TransportSession` table — both trusted a derived field kept in sync by two separate, unwrapped database writes with no atomicity between them, so a failure between those writes could leave a vehicle stuck `IN_TRANSIT` forever with the session itself correctly `COMPLETED`/`CANCELLED`. Fixed the cause: `startTransport()` now queries real session data via a new `findActiveForVehicle()` and self-heals stale data it finds rather than tolerating it; both places that end a session now wrap the session+vehicle writes in a real Prisma transaction, reusing the existing `update()` functions via a new optional `client` parameter. A related gap found during the investigation — one session's failure could silently skip every other session's checks for that watcher tick — was fixed alongside it. The frontend had an independent copy of the same mistake (the button label checked the same stale field, disconnected from the mount-time logic that already checked real data); replaced with socket-kept-fresh real session tracking. 45/45 backend tests passing, no regressions, clean production build. See `docs/chainguard-critical-bugfix-vehicle-status-desync.md`.

**Known, deliberate gaps (not bugs):**
- No AI inference service exists yet (`ai/` directory) — `Analytics` and `AI Detection` charts that depend on real detections will show empty states until seeded/generated data exists.
- `Report` generation creates a database record but does not yet render an actual downloadable PDF/CSV file.
- `Detection` records have no relation to `Envelope` records in the schema yet — per-envelope AI observations aren't possible until that link is added (planned for the AI module phase).
- No GPS/Transport/Simulation modules yet — planned for a later phase.
- Profile image upload has a schema field (`profileImagePath`) but no upload UI or endpoint wired yet.
- Settings' Notification Preferences, Theme, Database, API Keys, and AI Model tabs remain cosmetic-only placeholders (pre-existing from before Phase 1, not newly introduced) — Theme in particular is an intentional non-goal, since the app's design language is fixed dark-theme throughout.
- Account deactivation/deletion takes effect within the access token's lifetime (≤15 minutes), not instantly — there is no token revocation list. A refresh attempt is blocked immediately; an already-issued access token remains valid until it naturally expires.
- A user cannot yet view their own extended profile fields (employee ID, department, etc.) from Settings — `GET /users/:id` is Administrator-only, with no self-view exception yet.
